# Запуск в Telegram — чек-лист

Пять шагов. Токен живёт только в двух местах на выбор: в секретах GitHub или в файле `.env`
на твоём компьютере. В файлы репозитория и в переписку он не попадает никогда.

## 1. Токен

Токен, который однажды попал в коммит `90b989b`, считается засвеченным: такие значения
автоматические сканеры собирают из публичных репозиториев за минуты.

- [ ] В [@BotFather](https://t.me/BotFather): `/revoke` → выбрать бота → получить новый токен

Дальше новый токен кладётся в одно из двух мест — выбери путь.

### Путь А — без терминала (через секреты GitHub)

Подходит, если правишь проект через сайт GitHub. Токен хранится в зашифрованном хранилище
GitHub, в файлы репозитория не попадает и в логах маскируется.

- [ ] **Settings → Secrets and variables → Actions → New repository secret**
      имя: `BOT_TOKEN`, значение: новый токен → **Add secret**

Секрет виден только раннеру во время запуска: ни в коде, ни в интерфейсе его больше не прочитать.

### Путь Б — локально (через `.env`)

Подходит, если папка проекта лежит на компьютере и есть терминал.

```bash
cp .env.example .env
nano .env          # или открыть любым редактором
```

```
BOT_TOKEN=новый_токен_от_botfather
APP_URL=https://my-body-upgrade-app.vercel.app
```

`.env` закрыт в `.gitignore` — он остаётся на твоём диске и никуда не уходит.
Файл начинается с точки, поэтому скрыт: в Finder показать его — `Cmd+Shift+.`,
в проводнике Windows — **Вид → Показать → Скрытые элементы**, в VS Code виден сразу.

Никогда не вписывай токен в `tools/setup-bot.sh`, в `.env.example`, в README или в любой другой
файл репозитория: всё, что там лежит, уходит на GitHub. И не присылай его в переписке.

## 2. Защита от повторной утечки

- [ ] На GitHub: **Settings → Code security → Push protection** — включить.
      Это работает и для правок через сайт.

Если работаешь локально, дополнительно:

```bash
git config core.hooksPath .githooks   # хук отменит коммит с секретом
./tools/check-secrets.sh --history    # проверка, что ничего не утекло
```

## 3. Мини-приложение в BotFather

Эту часть Bot API не умеет, только руками, один раз.

- [ ] `/newapp` → выбрать бота
- [ ] Название, короткое описание
- [ ] Иконка 640×360
- [ ] URL: `https://my-body-upgrade-app.vercel.app`
- [ ] Короткое имя приложения

На выходе получишь прямую ссылку вида `t.me/<бот>/<приложение>` — её можно слать кому угодно.

## 4. Настройка бота

Скрипт ставит кнопку меню, имя, описания и команды.

**Путь А (без терминала):** вкладка **Actions** → слева «Настроить бота» → **Run workflow** →
адрес приложения уже подставлен → **Run workflow**.

**Путь Б (локально):**

```bash
./tools/setup-bot.sh
```

Скрипт сам читает `.env` и вырезает токен из любого вывода. Ожидаемый результат в обоих случаях:

```
Бот:
  @твой_бот
Приложение: https://my-body-upgrade-app.vercel.app

Настраиваю:
  ok  setChatMenuButton
  ok  setMyName
  ok  setMyShortDescription
  ok  setMyDescription
  ok  setMyCommands
```

Совсем без автоматики то же самое делается руками:
`/mybots` → бот → **Bot Settings → Menu Button** → вставить адрес приложения.

## 5. Проверка

- [ ] Открыть чат с ботом, нажать кнопку меню — приложение открывается на весь экран
- [ ] Свайп вниз не закрывает приложение во время тренировки
- [ ] В профиле блок «Аккаунт Telegram» показывает твоё имя и «синхронизировано»
- [ ] Закрыть квест, потом открыть приложение с другого устройства под тем же аккаунтом —
      журнал должен подтянуться сам

Отладка на компьютере: Telegram Desktop → правый клик по мини-приложению → «Inspect».

# Сервер журнала: Postgres на Vercel

Журнал переезжает с устройства на свою базу. Бесплатно: база Neon через маркетплейс Vercel
(Vercel Postgres теперь и есть Neon). Тарифы Hobby у обоих — для себя и друзей, не для продажи.

Пока сервер не настроен, приложение работает как раньше: устройство + облако Telegram.
Ничего не ломается и в промежуточных состояниях.

## 6. База

- [ ] Vercel → проект → **Storage → Create Database → Neon (Serverless Postgres)**
- [ ] Регион — **Frankfurt (eu-central-1)**: функции приложения тоже во Франкфурте (`vercel.json`),
      запросы не летают через океан
- [ ] **Connect** к проекту для окружений Production и Preview — Vercel сам пропишет `DATABASE_URL`

Строку подключения никуда не копируй: ни в файлы, ни в переписку. Она живёт только в переменных Vercel.

## 7. Переменные окружения

Vercel → проект → **Settings → Environment Variables**:

| Имя | Значение | Отметить |
|---|---|---|
| `BOT_TOKEN` | токен бота (тот же, что в `.env`) | **Sensitive** |

Регистрация открытая: любой, кто открыл приложение через бота, заводится в базе сам при первом
запуске. Кто это, сервер узнаёт по подписи Telegram — подделать её без токена бота нельзя.
От злоупотреблений: не больше 5 новых аккаунтов с одного адреса в сутки и 100 всего в час;
когда база подходит к 400 МБ из бесплатных 500, новых не заводим (у них приложение работает
как раньше — на устройстве и в облаке Telegram), а у уже заведённых всё продолжает работать.

Нужна закрытая бета — добавь `ALLOWED_USERS`: через запятую `@username` или числовые id
(`vsevolod214,ivan_petrov`). Тогда сервер пускает только их. Поменял переменную — **Redeploy**.

## 8. Деплой и проверка

- [ ] Слить PR в `main` → Vercel соберёт сам
- [ ] Открыть `https://<твой-адрес>.vercel.app/api/health`. Должно быть:
      `{"ok":true,"configured":true,"db":"ok","schema":1,"rls":true,"isolation":"role"}`
  - `configured:false` — нет `BOT_TOKEN` или `DATABASE_URL` (шаги 6–7, потом Redeploy)
  - `db_unavailable` — база не подключена к проекту или спит (у Neon первая побудка ~1 с, обнови страницу)
  - `rls:false` — что-то не так со схемой; ничего не делай с данными и напиши мне

### Переезд журнала @vsevolod214

- [ ] Открыть бота **на том телефоне, где весь журнал** (основном)
- [ ] Профиль → блок «Аккаунт Telegram»: статус «синхронизировано», подпись
      «Журнал хранится на сервере, копия — в облаке Telegram»

Что происходит под капотом и почему данные не потеряются:
1. Сначала приложение сверяется с облаком Telegram — если там журнал свежее (с другого телефона),
   переезжает именно он.
2. Копия журнала «до переезда» остаётся на телефоне (`…before-server` в хранилище).
3. На сервер журнал пишется только если там пусто; повторный «переезд» поверх существующего
   сервер отклонит.
4. Первая запись помечается в истории версий как `migrate` и хранится всегда. Кроме неё —
   30 последних версий (не чаще одной в 15 минут, не больше 15 МБ на человека).
5. Облако Telegram продолжает получать копию — это вторая резервная.

После этого второй телефон или Telegram Desktop забирают журнал с сервера сами.
Если журнал менялся на двух устройствах сразу, приложение спросит, какую версию оставить,
а вторую сохранит резервной копией на устройстве.

## 9. Необязательно: отдельный логин приложения (жёсткая граница)

По умолчанию запросы пользователей идут от владельца базы с понижением роли до `bu_app`
(у неё нет права обходить RLS). От SQL-инъекций защищает то, что все запросы только с
параметрами — это проверяют тесты. Чтобы и теоретически любой запрос оставался в пределах
своего пользователя, дай приложению отдельный логин без прав владельца:

- [ ] Neon (Vercel → Storage → база → **Open in Neon**) → **SQL Editor**, после шага 8:
      ```sql
      CREATE ROLE bu_web LOGIN PASSWORD 'длинный-случайный-пароль' IN ROLE bu_app;
      ```
      Пароль — случайный, 30+ символов (менеджер паролей сгенерирует).
- [ ] Vercel → переменная `DATABASE_URL_APP` (**Sensitive**) = та же строка, что `DATABASE_URL`,
      но с `bu_web` и этим паролем вместо пользователя и пароля → Redeploy
- [ ] `/api/health` теперь показывает `"isolation":"login"`

## Откат журнала из истории версий

Neon → SQL Editor. Запросы выполняются от роли приложения и видят только строки
указанного пользователя — так же, как сервер. Свой числовой id в Telegram подскажет @userinfobot.

```sql
BEGIN;
SELECT set_config('app.user_id', '123456789', true);   -- id в Telegram
SET LOCAL ROLE bu_app;
-- версии: какая была когда
SELECT id, rev, reason, created_at, jsonb_array_length(data->'sessions') AS sessions
FROM journal_versions ORDER BY id DESC;
COMMIT;
```

Вернуть выбранную версию (ревизия растёт — устройства заберут её как обычное обновление):

```sql
BEGIN;
SELECT set_config('app.user_id', '123456789', true);
SET LOCAL ROLE bu_app;
UPDATE journals j SET data = v.data, rev = j.rev + 1, updated_at = now()
FROM journal_versions v WHERE v.id = <id версии> AND j.user_id = v.user_id;
COMMIT;
```

## Когда переедем со своим доменом

Всё серверное лежит в `server/` и не зависит от Vercel: `tools/dev-server.mjs` поднимает то же
приложение с тем же API на обычном Node + Postgres (`DATABASE_DRIVER=pg`). За nginx — пробросить
`X-Real-IP` и `Host`, база — с отдельным логином из шага 9.
